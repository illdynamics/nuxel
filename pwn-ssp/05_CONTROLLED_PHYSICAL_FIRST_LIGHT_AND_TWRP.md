# 05 — BOUNDED REAL FIRST-LIGHT TRIAL AND TWRP BOOT-ONLY RECOVERY LOOP

DeepSeek-V4-Pro-Thinking: MASTER 00, stages 01-04, especially a **fully PASS** `SSP-CANDIDATE-PREFLIGHT.json`, govern every operation. This phase can make explicitly approved hardware changes; never perform them before all prerequisites. No DTB/DTBO/RECOVERY/bootloader/other partition writes, ever.

## Go/no-go before touching hardware

- Healthy Nuxel and accessible TWRP demonstrated, exact partition identity checked, BOOT donor + two immutable known-good rollback copies verified, selected DTBO index and DT tail hashes recorded. All fixes and full tests/build complete; no unresolved deadlocks, parser truncation acceptance or missing mandatory patches.
- Owner's established TWRP agreement covers **verified BOOT-only** candidate reflashing when needed. Identify the exact single target by validated `by-name`/partition mapping, candidate hash/bytes, expected readback and rollback. Do **not** flash if map or verification cannot be established. If live hardware rail cycle or RAM firmware load is not covered by a reviewed bounded trial, get the owner's separate go-ahead before triggering it.
- Guarantee a single initializer/transport owner and coherent runtime service ordering; prevent auto-start collisions and repeated systemd resets, disable any uncontrolled auto-retry path using a reversible service override if needed. Define maximum **one** firmware attempt per trial and bound reset/cycle count (prefer zero unless source-verified necessary), total session duration and abort codes; each retry needs diagnosis and evidence, not just delay.

## Execution protocol

1. Capture **pretrial read-only** Nuxel state and recent logs, services, SPI runtime PM, chip/rail ownership, line/IRQ diagnostics, boot identity and read-only DT hashes. Never probe private partitions or dump personal storage.
2. For a BOOT candidate that passes gate, enter TWRP using the established manual procedure. Reverify recovery mode and partition mapping; stage the exact artifact; compare device-side SHA-256. Write **only validated BOOT**, sync and verify partition readback against the candidate digest and size. Do not alter external DTB or DTBO, even if the candidate fails to boot. Preserve recovery accessibility.
3. Reboot deliberately into **normal Nuxel**. If it unexpectedly returns to TWRP, candidate = **FAIL**, even after a successful write. Collect bootreason and available recovery logs, correlate image/DT tail/header/state; if unclear, restore **original known-good BOOT** in TWRP, verify readback, reboot to Nuxel and verify SSH/systemd. If a concrete fix is identified, revise offline and repeat stages 02-04 before the next candidate. Do **not** blindly repeat the same image. If known-good also fails, stop in TWRP safely and report, **do not touch DT**. Bound revised candidate attempts, recover Nuxel with the original known-good image before escalating.
4. Once Nuxel is healthy, run the explicitly reviewed, **single bounded MCU first-light test**. Do not claim the rail cold-cycled merely because a regulator API returned 0; record regulator shared consumers, reference counts, PMIC state/voltage proof if available, SPI command shape and timestamps, GPIO levels/IRQ counters. Avoid repeated `regulator_force_disable` and GNSS collateral risk.
5. Observe the first real bidirectional **ROM GetVersion** after autobaud: validated framing, CRC, payload length, expected ID, version/ASIC, session. If reads stay `0xffffffff`, RX is zero or the hub does not assert a response, immediately stop and classify failure under: clock/PM, pinmux/mode, chip-select, rail/reset/standby, boot-ROM timing, wrong device/firmware, driver concurrency, incomplete parser. Do not send hundreds of speculative firmware writes when no validated MCU response exists.
6. Only on valid ROM identity, perform bounded, record-by-record RAM firmware writes using the chosen single transport owner. Require every F1 and any non-F1 vendor-defined operation to complete with the correct *operation-level* receipt (if the vendor contract requires more than a reliable ACK, implement it). Stop on NACK, out-of-sequence, missing data, wrong version, CRC failure or timeout. Then validate app start, post-start version, normal SSP WHOAMI, scan and sensor availability. Do not issue manual/fake `ESW:READY` to force a green outcome.
7. Capture posttrial dmesg, journals, precise state transitions, per-stage byte counts/reply hashes, service status, Nuxel UI/SSH/network/display, read-only external DTB/DTBO hashes and running kernel identity. Restore any temporary service override, regulator state and transport owner. If firmware test failed, leave the phone safely in a bootable Nuxel with truthful `SSP_NOT_READY`; don't leave it in an automatic reset storm.

Do not conflate passing unrelated items.
