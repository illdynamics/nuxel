# 03 — SOURCE-VERIFIED BCM47752 ROM, RAM FIRMWARE AND COLD-START CONTRACT

DeepSeek-V4-Pro-Thinking: carry MASTER 00 and stages 01-02. Research/reverse-engineer and test **offline first**, without live hardware changes. Work from version-matched pinned original Samsung `lhd`, the active vendor kernel source and existing repo analyzers. Do not reintroduce Android/Bionic into production.

1. Identify exact pinned `lhd` binary by SHA256, firmware container identity, chip/board version matching, vendor protocol revision, legacy `lhd.conf` GPIO/SSI settings and all newer reports. Archive reports propose ASIC 0x004775b0, 438895 B decoded F-records, patch entry 0x00800161, IEEE blob CRC32 0x93d35bb4; **recompute** from the recovered real header/build files. Do not confuse vendor `Crc` with IEEE CRC32.
2. Reconstruct the vendor's **actual** full protocol: initial regulator/reset/standby ordering; SPI host state; ROM autobaud length/transfer mode; GetVersion request/expected reply; reliable session setup; exact F0..F5 record grammar; MemoryWrite command (RPC ID 5) operation-level acceptance; StartScratchApp (46), ServiceStart (55), final version, READY conditions, WHOAMI and sensor enumeration. Differentiate reliable transport acknowledgment from RPC completion. Cite ELF offsets/source functions and provide confidence levels.
3. Use existing `tools/s10plus/ssp-runtime/inspect_lhd_init.py`, `replay_lhd_response.py`, `check_protocol_replay.py`, and `tools/s10plus/ssp-native` tests instead of inventing a third protocol stack. Characterize both normal and faulty replies including short packets, wrong CRC, stale ACK, seq wrap, mixed ROM/application versions, duplicate replies and disconnects.
4. Resolve the reported **cold-start timing** from actual evidence: when MCU rail truly turns on/off, when SPI clocks and IRQ become available, whether bootloader leaves rail enabled without kernel reference, whether warm reset can re-enter ROM, whether `mcu_resp=1` means meaningful response, and whether SPI `0xFF` is electrical idle rather than protocol reply. Compare early-userspace, initramfs and kernel-coordinated approaches with their boot chain and power implications; select the least invasive viable design. A timing guess or arbitrary `sleep` is not a root-cause fix.
5. Produce a rigorous state machine: `HW_UNKNOWN -> ROM_SYNC -> ROM_VERSION_VERIFIED -> FW_TRANSFER -> FW_TRANSFER_COMPLETE -> APP_VERSION_VERIFIED -> SSP_HANDSHAKE -> ENUMERATED -> STREAMING`. Each transition has exact expected message/bytes, timeout, retry policy, error code and cleanup. No false READY. Single owner of MCU power and BBD transport.
6. Put a guard around firmware load (version/digest/matched board), run at a moment when MCU is actually ready, and refuse to download if startup identity is unknown. Do not treat on-device firmware RAM writes as permanent storage flashing; still treat them as potentially disruptive and require a bounded approved physical session.

**Deliverables:** `reports/SSP-VENDOR-PROTOCOL-PARITY.md` (source references and exact semantics), `reports/SSP-COLD-START-TIMELINE.md` (which parts measured vs hypotheses), offline replay/golden-frame corpus, precise chosen architecture, no speculative GPIO/reset steps. PASS only with defined acceptance criteria for each firmware stage and conclusive preflight tests.
