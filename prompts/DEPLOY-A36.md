# Nuxel A36 — live USB deployment work order (MacBook → S10+)

Continue from the current running Nuxel checkout and read `docs/s10plus-autonomous-boot-repair/TOUCHDOWN/A36-ICON-AUDIO-IMPLEMENTATION.md`. This checkout includes the owner-supplied navigation PNGs, app/Quick Settings icon packs, the **7.7s** `nuxel-boot-audio.mp3`, and the **0.37s** `nuxel-pow.mp3`.

**Do not flash anything.** Do not modify BOOT, USERDATA, EFS, partitions, bootloader, modem, kernel or recovery state. Use only the existing framed USB live console; preserve single-owner port locking and rollback receipts.

1. Verify the actual serial port, live phone mode and authoritative nuxel-web document root. Capture installed hashes/backups before writing. Run `python3 tools/s10plus/a34/tests/test-sound-cues.py`, `test-icon-assets.py`, and `bash tools/s10plus/a34/tests/run-a34-tests.sh`.
2. Apply the new `nuxel-branding-sounds-and-icons` extension group in `tools/beta/live/deploy-manifest.json` using the existing guarded live deployer; it transfers the 22 actively referenced PNGs, both MP3s, the sound-cue helper, unit and haptics source/preferences. Check source/destination checksums. The remapped phone webroot is normally `/usr/share/nuxel/assets`, but measure it rather than guessing.
3. Verify HTTP 200 and `image/png` for `/assets/button-left.png`, `/assets/button-middle.png`, `/assets/button-right.png`, `/assets/nuxel-applications-icon-pack/01-01_terminal.png` and `/assets/nuxel-quicksettings-icon-pack/01-wifi.png`. Make the PWA reload new assets/cache without losing session state; verify all 3 custom button icons, launcher, Recents, search and quicksettings actually render their PNG art.
4. Install/check `mpg123` on Fedora using supported repositories. Validate `/usr/libexec/nuxel/nuxel-sound-cue` is executable, service unit staged, and do `systemctl daemon-reload && systemctl enable nuxel-boot-sound.service`. The boot cue is triggered by the real `/run/nuxel-anim-handoff` JSON ownership receipt, **not** by early web load. It requests 44% PCM gain while preserving the existing S10+ 25% protective ALSA mixer cap; don't remove that safety cap without verified speaker output.
5. Build the current A34 patched `nuxel-button-manager.c` for **Linux AArch64** with ALSA headers. Verify ELF architecture and dependencies; back up and atomically install `/usr/lib/nuxel/nuxel-button-manager` through the USB console. Restart only `nuxel-button-manager.service`. This patch requests `nuxel-pow.mp3` immediately after each *successful* mixer change at the actual new mixer volume, while rate-limiting overlap and honoring mute/vibrate mode.
6. Inspect existing `nuxel-haptics.service` and older `nuxel-haptics-bridge.service` before enabling anything: only one service may write the vibration motor. The staged preferences have tap 12 ms, scrolling 6 ms, long press 25 ms and default intensity 30%. Verify actual vibrator capability and expose unsupported amplitude honestly.
7. Tell me a **90-second test starts NOW**: tap launcher/dock/back/home/recents, open Quick Settings, adjust Volume +/- multiple times and tell me whether the new MP3 feedback is audible immediately at each new level; feel whether haptics behave appropriately. Collect actual speaker/haptics/runtime logs. Continue automatically after capture.
8. When safe and the live console can reconnect, perform one **normal Nuxel reboot**. Confirm the *7.7s* boot sound starts only after the real animation→launcher ownership handoff, plays once, and does not repeat on bridge restart. Check `/var/log/nuxel/sound-cues.log` and the systemd journal. Ask for explicit owner PASS/FAIL. If audio is silent despite successful decoding, investigate the existing ALSA/DAPM/speaker route—do not claim success from mpg123 exit code alone.

Fix any failure and repeat a bounded test. Restore previous binaries/assets if UI or audio regress. **Never flash.** Report verified tests, installed SHA-256 hashes, and which physical owner checks remain pending.
