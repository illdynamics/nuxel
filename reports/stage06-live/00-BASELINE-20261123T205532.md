## CRITICAL DECODE FINDING (authoritative, from IpcRxNetRegState disasm)
The IpcRx* receive handlers take `char* data` = FULL FMT frame (header+payload),
NOT the payload. Verified via IpcRxGeneral (GEN echo) which reads data[7]=echo_main,
data[8]=echo_sub (i.e. payload[0], payload[1]).

Therefore IpcRxNetRegState @0x339818 reads:
  data[6] = header cmd_type (registrant selector: 0x03 => data/PS response)
  data[7] = payload[0] = RAT marker
  data[8] = payload[1] = service-domain selector (int map @0x14a0b8: {1->0,2->2,3->1})
  data[9] = payload[2] = RegState selector (=> RegState enum)
  data[10]= payload[3] = reject cause
  data[11..12]= payload[4..5] = LAC/TAC (LE halfword)
  data[13..16]= payload[6..9] = cell id (LE word)
  data[17] = payload[10] = LtePsVoiceIndication
  data[18..19]= payload[11..12] (halfword)
  data[20] = payload[13] = secondary service domain
  data[21] = payload[14] = secondary RegState

Applied to live payload:
  payload[1] = 0x03 => service domain selector 3 => NetServiceDomainType 1 (PS_ONLY)
  payload[2] = 0x01 => RegState = REGISTERED_HOME (1)   [IsRegistered: (r|4)==5 => r in {1,5}]
  payload[3] = 0x00 => reject cause 0 (none)
  payload[0] = 0x01 => RAT marker 1 (via helper table)

CONCLUSION: The modem ALREADY reports PS/data registration = REGISTERED_HOME.
The current Nuxel code reads payload[8]/payload[9] (WRONG) and falsely reports
"NOT_REGISTERED(0)" + "domain unconfigured(0)". This false-negative blocks the
FSM at PS_REGIST_VERIFY, so the data call / PDP activation never runs.
The round-14 report also used wrong offsets (payload[1]/payload[2] as PS/CS),
falsely concluding "PS DENIED".
