## Root cause

The first broken stage was **callback invocation**, not threshold geometry or
coordinate math. `lockscreen.js` was wrapped in `(function () { ... })()` but
used a bare `global` identifier in `_buzz()`, `_trace()` and the battery/host
checks. In WebKit there is no `global` binding. The release path therefore ran:

```
pointerup -> _unlock() -> _buzz() -> ReferenceError: Can't find variable: global
```

and execution stopped before `NuxelHost.action('unlock')`. The overlay stayed
mounted and the compositor never received an unlock request.

Live evidence captured before the fix (original A45 build):

```
EVT pointerdown x=188 y=547 tag=IMG id=lockscreen-handle
...
EVT pointerup x=173 y=325 tag=IMG id=lockscreen-handle
JS-error ReferenceError: Can't find variable: global
         @http://127.0.0.1:8000/pwa/nuxel-home/js/lockscreen.js?v=a45:167
```

The drag followed the finger correctly because its event listeners were bound
before the throwing constructor paths; only the release-side callback was lost.

## Source changes

### `pwa/nuxel-home/js/lockscreen.js`

- Bind the IIFE to `window`: `(function (global) { ... })(window);` — the direct
  root-cause fix.
- Rebuild the drag lifecycle as an explicit per-gesture state machine:
  `IDLE -> TOUCH_CAPTURED -> DRAGGING -> THRESHOLD_REACHED -> UNLOCKING -> UNLOCKED`;
  cancellation returns to rest and then `IDLE`.
- Use one gesture object with a unique id, pointer id, start/release coordinates,
  signed upward distance, effective threshold and one-shot guards
  (`released`, `requested`, `consumed`, `acknowledged`).
- Use `clientY` viewport CSS pixels consistently. The threshold is 22 % of the
  usable height, clamped to the handle's real travel:
  `threshold = min(0.22 * vh, restTop - 24)`. On the S10+ (360x760 CSS):
  `min(167, 555) = 167 px`.
- Handle `pointerdown`, `pointermove`, `pointerup`, `pointercancel` and
  `lostpointercapture`; window-level capture-phase `pointermove`/`pointerup`
  fallbacks complete a release outside the icon rectangle. Duplicate
  release/cancel events are ignored per gesture.
- Use the release event's final `clientY`, so a coalesced final move still
  completes the swipe.
- A completed swipe asks the trusted launcher controller first:
  `nuxel.unlockFromLockscreen(instance, request)`. The overlay is hidden only
  after a successful acknowledgement; a backend error/refusal snaps back and
  leaves the session locked.
- Add a subtle `.armed` glow at threshold. The artwork, resting position, size,
  wallpaper composition, clock, date and battery indicators are unchanged.

### `pwa/nuxel-home/js/app.js`

- Add `unlockFromLockscreen(instance, request)` as the single gesture-to-session
  handoff. It verifies the request came from the active lockscreen instance and
  consumes the one-shot gesture id.
- Ask the existing native host for `unlock`, then apply the authoritative
  launcher/session transition only after `ok` is returned.
- `_unlock()` now returns a result object, resets the stale display-off sample
  and records an unlock generation.
- Fix a second latent bug found during live verification: the relock watcher
  matched only `^DISPLAY_OFF`, while the running bridge publishes
  `display=off`. It now accepts both forms. A stale OFF sample after unlock is
  treated as unknown (`_lastDisplayOff = null`) so it cannot immediately
  re-lock; the next observed ON->OFF transition still locks.

### `pwa/nuxel-home/index.html`

Cache-busting revisions changed to `?v=a451` for `lockscreen.css`,
`lockscreen.js` and `app.js`, so WebKit cannot run the stale A45 bundle.

### `pwa/nuxel-home/css/lockscreen.css`

Added only `.lockscreen-handle.armed` (subtle threshold glow). No geometry,
position, artwork or existing style was changed.

### `tools/s10plus/a45/test-lockscreen-unlock.js`

New mocked regression harness (47 checks): small drag, sufficient drag, release
outside the hitbox, pointer cancel, lost capture, downward drag, tap, one request
per gesture, backend error/refusal, successful acknowledgement, locked/unlocked
input, Power relock, display-off format, stale-OFF behavior, 60 s idle source
invariants, repeated cycles, focus after unlock, coalesced release, and cold-boot
lockscreen.

## Security notes

- No new privileged endpoint was introduced. The gesture path uses the existing
  typed host verb `unlock` and the existing launcher controller.
- `unlockFromLockscreen` only accepts the active lockscreen instance and a
  one-shot gesture id whose recorded distance, threshold, reached/released flags
  and consumed state match. A replayed request is refused.
- Untrusted synthetic DOM events (`isTrusted === false`) are ignored.
- This remains a convenience swipe lock, not PIN authentication. No separate
  authenticated security lock is bypassed.

## Owner physical acceptance (required)

1. Wake the S10+ and confirm the lockscreen wallpaper, clock, battery and
   lockhead appear exactly as before.
2. Short drag upward and release: the lockhead must snap back and stay locked.
3. Full upward drag and release: the lockscreen must disappear.
4. Confirm Home Desktop 1 (cold boot) or the previously active application
   (power/idle lock) is interactive.
5. Touch an application and confirm it responds.
6. Press Power, wake, unlock again.
7. Tap a text field and confirm the Stevia keyboard appears and types.
8. Leave the phone idle for 60 s and confirm the panel turns off; wake and
   confirm the lockscreen returns.

Physical finger confirmation is the only remaining gate. Synthetic integration
does not count as physical acceptance.
