# Nuxel v0.7.0-beta — Tri-Link consoles, real hardware providers, GPS/Maps truth

**Released:** 2026-10-27
**Device under test:** Samsung Galaxy S10+ SM-G975F (`beyond2lte`, Exynos 9820)
**Kernel:** Samsung-derived Linux 4.14.253 (unchanged; no kernel/partition flash)
**Userspace:** Fedora 43 aarch64

## What shipped

This release merges the 25000–29000 work into `main` through one feature branch
and PR:

| Work | Result |
|---|---|
| 25000 Live Console++ | Serial Live Console keeps its exclusive lock, framed transport and verified output; indicators follow the real USB data link |
| 26000 Tri-Link | Explicit `serial` / `wlan` / `usb` / `auto`; pinned Ed25519 host key; public-key SSH; SHA-256 put/get; exit codes preserved |
| 27000 GPS | Canonical Location provider; Maps consumes real provider state; pins/cached coordinates are never a fix |
| 28000 Tri-Link UI | Three console entries registered exactly once; unlock → Home repair; launch handlers verified |
| 29000 Hardware | Bluetooth, Location, Audio and Displays Settings pages share the authoritative Quick Settings providers |

The live userspace artifact is generated from the same commit by
`tools/s10plus/a43/package-live.py` and verified by `verify-live.py`. The release
workflow rebuilds the S10+ image set from that commit; the phone was updated
live from the same repository bytes with SHA-256 staging, atomic install,
coalesced service restarts, health checks and automatic rollback.

## Device verification performed

- **Three consoles** — all three app pages and registry IDs resolve; the
  Application drawer launches `org.nuxel.LiveConsole` (Serial), `org.nuxel.USBSSHConsole`
  and `org.nuxel.WiFiSSHConsole`; Wi-Fi SSH executes real commands over the
  pinned host key; USB SSH reports `BLOCKED_KERNEL_PANIC` from the NUXEL-26000
  teardown evidence rather than claiming a connection.
- **GPS via the app/provider** — the canonical location state machine reports
  provider availability, permission and fix quality separately. No fix is
  fabricated; Maps surfaces the same state.
- **Bluetooth** — the BCM4375 radio/rfkill is present and the owner-supplied
  HCD is SHA-256 verified (`35fd013f…`). The running kernel, however, has
  `CONFIG_BT_HCIUART` **not set**; `bcm43xx_bluetooth` is only the power/rfkill
  driver. Therefore no `hci0` can register and scanning cannot return devices.
  The provider now reports `BLOCKED_KERNEL` with this exact evidence.
- **Audio** — real ALSA cards (`beyond-madera`, `abox_vdma`, `abox_dump`),
  playback/capture PCMs and the discovered `HPOUT1 Digital` control are
  reported; low-volume set/readback works. Audible output is left for the
  owner's physical confirmation. `HPOUT1 Digital` unmute still wedges in
  kernel D-state and is refused rather than half-offered.
- **Known-good regression surface** — Wi-Fi, browser, shell, lockscreen,
  charging indicator and the serial Live Console remain reachable.

## Remaining blockers (not faked)

1. **Bluetooth scanning:** kernel `CONFIG_BT_HCIUART` is unset. A scoped kernel
   rebuild with the HCI UART transport (and then the verified HCD) is required.
2. **GNSS:** no BCM4773 GNSS firmware/reader in the vendor blob set; no
   coordinate may be claimed.
3. **USB-C HDMI:** `CONFIG_DRM` is not set and the Type-C DP Alt Mode stack is
   absent; Mirror/Desktop cannot be driven by userspace.
4. **Audio unmute:** MADERA `HPOUT1 Digital` unmute enters kernel D-state; the
   UI reports mute as unsupported and refuses the write.
